# 产品文档中心 — 需求规格文档（含对话澄清归档）

> 版本：v1.0（2026-09-25）｜配套文档：《文档中心-设计与实现技术文档》《企业级文档中心解决方案.md》
> 用途：完整归档需求提出与对话过程中的澄清细节，作为后续迭代的需求基线。

---

## 1. 项目背景

公司内部 **4 条产品线、每线不少于 8 款产品、累计 20+ 活跃在研产品/项目**，每产品存在多版本、多语言（简体中文/繁体中文/英文）文档需求。需建设统一文档中心，实现编写、管理、发布（Web + PDF 离线分发）一体化。

> 原型阶段范围（已确认）：以 3 条产品线、9 个代表产品做 Demo 验证；语言先支持简体中文 + 英文；每产品 V1.0/V2.0 两个版本。

## 3. 技术选型确认（对话中拍板）

- **SSG：Docusaurus 3.x** —— 用户明确认可（"SSG方案选择 Docusaurus，我认可你的这个方案"）。选型依据：唯一同时原生满足多产品/多版本/多语言三项硬需求（对比 VitePress、MkDocs 的结论见解决方案文档）
- **Monorepo 单仓多实例**：20+ 产品同仓统一治理，站内每产品为逻辑独立"文档小站"；权限隔离用 GitLab 目录 CODEOWNERS（4 条产品线同一团队体系内，粒度够用，不拆仓）
- **PDF 管线：Paged.js + Puppeteer**（MIT 开源，替代 Prince XML 商用方案）

## 4. 对话澄清细节归档（按时间序）

### 4.1 概念澄清：Monorepo 单仓多实例
用户追问该术语含义，已解释：单仓库（统一 CI 门禁/工具链/依赖）+ 站内每产品独立 docs 插件实例（独立路由前缀/侧边栏/版本集/i18n）。权衡点：权限隔离粒度弱于独立仓库，判定够用。

### 4.2 原型范围界定（用户指定）
- **3 条产品线 9 产品**（Demo 用，非全量 20+）：
  - 中间件：应用服务器 AAS、分布式消息队列 ADMQ、分布式缓存 ADC、负载均衡器 ALB
  - 数据治理：主数据管理 AMDM、数据治理平台 ADGP
  - AI 平台：AI 网关 AIG、知识库平台 AKM、记忆平台 AMEM
- **每产品 7 个文档章节**：简介、快速开始、安装手册、使用手册、配置手册、开发手册、性能调优
- **先支持简体中文 + 英文**两种语言（繁体中文后续）
- **每产品 V1.0、V2.0 两个版本**（Demo 可模拟生成样例内容）

### 4.3 补充需求：版本/语言下拉切换
> 用户原话要点：查看某产品文档时，版本应通过**下拉列表**选择，语言也应通过**下拉列表**选择；此前未实现。

实现口径（对话中确认的方案）：
- 上下文感知：导航栏仅显示**当前浏览产品**的版本下拉（避免 9 个下拉堆叠）；语言下拉为全站统一的 localeDropdown
- 版本下拉与产品名 chip 组合显示在导航栏右侧；非文档页（首页）自动隐藏
- 切换版本保持当前页面映射（/aas/intro ↔ /aas/1.0/intro）

### 4.4 补充需求：多产品阅读定位（重点需求）
> 用户原话要点：多产品多版本站点中，选择某产品某版本后，阅读时可能不知道当前文档属于哪个产品。单产品站点不存在此问题，**多产品时必须明确显示当前正在查看/阅读的是哪个产品的哪个版本文档，这是重点要解决的**。

实现口径：每篇文档正文上方增加「当前阅读」上下文条 —— 产品线 / 产品名 + 版本徽章（双语适配）；导航栏版本下拉前增加产品名。已验证中文/英文 × V1.0/V2.0 四种组合。

### 4.5 补充需求：PDF 目录虚线引导线
> 用户原话要点：PDF 目录的标题和页码之间，是否应像传统 docx 目录一样有虚线连接到页码、更美观？**评估可行性，若不支持则维持现状也可**。

评估结论：**支持**（纯 CSS 弹性布局实现，与 target-counter 页码回填兼容）。已实现并截图验证：一级加粗、二级缩进、虚线落基线、页码右对齐。

### 4.6 全文检索（已完成，2026-09-25）
用户提出全文检索需求，此前中断。已定位根因并修复：docusaurus-search-local 的 `docsRouteBasePath` 默认 `["docs"]` 与多实例 routeBasePath（aas/admq/…）不匹配导致索引为空，显式声明 9 个产品前缀后索引正常生成（每语言根索引 + 9 产品索引共 20 个文件）。中英文关键词、首页根索引、文档页产品索引四场景端到端验证通过（结果含高亮、面包屑、上下文摘要）。细节见技术文档 §10.1。

### 4.7 PDF 发版全量出稿（实施中确认的口径）
- 发版 = 全产品 × 全语言组合出稿（原型内 9 × 2 = 18 份，实测 2 分 02 秒全部成功）
- 产物目录规范：`output/pdf/{product}/{version}/{lang}/`，与制品库命名约定一致
- CI 打 tag 触发全量出稿；冻结版修订走增量

### 4.8 补充需求：Red Hat 文档形态的导航重构（2026-09-25）

> 2. **去掉**正文上方的「当前阅读/中间件/应用服务器」上下文条；

对话确认的口径：

### 4.9 补充需求：PDF 出稿对齐 Red Hat 离线文档（2026-09-25）
> 用户提供了 Red Hat JBoss Web Server 7.0 Installation Guide 官方离线 PDF 作为参考样张，提出三点修订：
> 1. PDF 生成**书签**（outline），可点击跳转指定章节；
> 2. **封面自定义**，设计参考 Red Hat：每份 PDF 带封面，含公司 logo、产品名称、版本及文档版本、文档发布时间；
> 3. PDF 自动加入**公共页面信息**（如 Red Hat 的版权声明页）。

实现口径（对照 Red Hat 样张解析结果）：
- **书签**：`page.pdf({ outline: true })`（Chrome `generateDocumentOutline`），按 h1→h2→h3 自动生成书签树；封面标题改用 div 避免混入书签。实测 45 条书签、三级嵌套、页码定位准确（pypdf 验证）
- **封面**：重设计为 Red Hat 式白底版式 —— 顶部居中横版 logo（新建 `static/img/logo-horizontal.svg`，可整体替换企业 VI 标识）→ 产品名（大字）→ 版本号 → 文档名（加粗）→ 副标题 → 右下「密级 + 发布日期」。定制三层：CLI（`--doc-title/--logo/--date`）> `cover.config.json`（公司名双语/logo/副标题/密级）> 内置默认
- **公共前置页**：法律声明页（版权声明/商标声明/免责声明/技术支持/文档信息表），独立模板 `notice.zh-Hans.html` / `notice.en.html`（占位符渲染），插在封面后、目录前，与 Red Hat「Legal Notice」页对位；声明页与目录自动进入书签
- PDF 元数据 `<title>` 同步改为「产品名 版本 文档名」

### 4.10 补充需求：PDF 章节序号规范（2026-09-25）
> 用户原话要点：文档一级标题中文默认增加章节序号，使用「第一章，第二章，第三章，第十章」样式，序号和标题之间使用空格分隔；子标题增加层级序号如 2.1. / 2.2. / 2.3.1.，序号和标题内容之间无空格或其他分隔符；英文版参考 Red Hat，一级标题为 CHAPTER 1. / CHAPTER 2. 样式，序号和标题之间无空格符和其他分隔符。

实现与自主决策记录：
- **中文一级标题**：`第一章 产品简介`（全章名与标题之间一个空格）；支持 1–99 的中文数字（十一、二十一……）
- **子标题（中英文一致）**：`2.1.环境要求`、`2.3.1.参数说明` —— 层级小数序号以「.」结尾后直接接标题，无空格（严格按用户口径）
- **英文一级标题**：`CHAPTER 2.Quick Start` —— 序号 `CHAPTER N.` 后直接接标题（严格按用户口径「无空格符」）。注：Red Hat 官方样张实为 `CHAPTER 1. Title`（带一个空格），已按用户明确表述实现；如需切换为 Red Hat 原生样式，改 `generate.js` 中 `CHAPTER_SEP_EN` 常量为 `" "` 即可
- **作用范围**：仅 PDF 出稿（正文 h1/h2/h3 与目录条目同步带序号）；站点 Web 端标题不加序号
- **实现位置**：`generate.js` 的 `h1Prefix()/subPrefix()/zhChapterNum()`；序号注入在抓取聚合阶段完成，书签 outline 自动携带序号，页眉「章节名」同步更新
